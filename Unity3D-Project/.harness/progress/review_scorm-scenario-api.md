## Findings

### Medium

**H1 (recommended, pre-existing at 3cbe562). The legacy `AddObjective`/`AddInteraction` break the index invariant against `cmi.objectives._count` / `cmi.interactions._count`.**

Where:
- `Assets/SCORM/_Scripts/ScormManager.cs:918-922` (`AddObjective`): `studentRecord.objectives.Add(objective)` happens **before** `SetAndCache(...id)`.
- `ScormManager.cs:549-555` (`AddInteraction`): `studentRecord.interactions.Add(interaction)` happens before `WriteInteraction`.

What breaks:
- This order was already there at 3cbe562 (old `AddObjective`, lines 860-864); F002 kept it. If the LMS rejects the id, the local list runs one ahead of `_count`. Realistic causes: calls before `Initialize` or after `Terminate` (132/133), or any other LMS rejection of the id. Legacy ids are `urn:STALS:objective-id-<Count>`, so collisions are unlikely.
- From then on, every `UpsertObjective`/`RecordInteraction` (which use `studentRecord.*.Count`, lines 1014 and 598) writes to an index with a gap. The LMS answers 351, the call returns -1, and this lasts for the rest of the session.
- `GetObjectives()` also shows a phantom entry.

Why it is still requested (non-blocking): the new API depends on `Count == _count`, and F002 already rewrote both methods, so fixing it costs little.

Fix: use the same order as `RecordInteraction`/`UpsertObjective`:
- write the id;
- `Add` to `StudentRecord` only if the LMS accepted it;
- otherwise return without writing the other fields.

If you want to keep the legacy behaviour of showing the objective locally without an LMS, keep it explicitly only for `!IsLmsConnected` and document it. Add a test: an id is rejected (e.g. after `Terminate`, or with a duplicate id on resume), then `UpsertObjective` still lands at `_count`.

**H2 (blocking). `UpsertObjective` and `RecordInteraction` do not report failed LMS writes (architecture principle 5, C3).**

Where:
- `ScormManager.cs:1037-1048`: `UpsertObjective` ignores the `bool` from `WriteScore` and from the status/progress/description writes, and returns `index` anyway.
- `ScormManager.cs:646-698`: `WriteInteraction` returns `false` only when the id is rejected. Rejections of type, objectives, response, result and so on are lost. Note that `type` failing silently also turns off `learner_response`/`correct_responses`, with no sign to the caller.

Why it matters: `UpdateScore`/`UpdateStatus`/`UpdateProgressMeasure` do return `false`, so the new surface is inconsistent with itself. `StudentRecord` stays consistent, because it is only updated on success, but the F003 tracker cannot tell "saved" from "partially rejected" without listening to the event.

Fix (keep the current return type for compatibility), any one of:
- add an `out bool allWritten` overload;
- return a small result type (`index` + `allWritten` + first error code);
- or document and expose `ScormManager.LastWriteFailed`/`LastErrorCode` for the call.

Add a test that forces a rejection of a non-id field and checks that it is reported.

**H3 (blocking). The `ScormCall`/`CallCompleted` event has no reentrancy guard.**

Where: `Assets/SCORM/_Scripts/ScormAPIWrapper.cs:277-289` (`Raise`).

What breaks:
- A handler that calls any SCORM operation re-enters `Raise` with no limit. Example: a log UI that does `SetLocation`/`Commit`, or that reads with `GetValue`. A handler that writes on every Set recurses forever, and a `StackOverflowException` cannot be caught: it kills the WebGL tab.
- A nested call also overwrites `LastErrorCode` (set at lines 195/260/269 **before** `Raise`). `ScormManager.LoadValue` (`ScormManager.cs:141`) reads it **after** `Raise`, and so does any caller that consults `LastErrorCode`. Today the impact is small (at worst a value is not cached and is re-sent), but it is fragile.
- The leader asked about this explicitly.

Fix:
- add a static `_raising` flag in `Raise`. Nested calls run normally but do not raise the event, or are queued and raised when the outer call finishes;
- capture `LastErrorCode` in a local before `Raise` and restore it after;
- document in `CallCompleted`/`ScormCall` that handlers must not call the SCORM API;
- add a test with a handler that calls `ScormManager.SetLocation` inside the handler.

### Low (non-blocking; fix them in the same round if they are cheap)

**L1. Numeric comparison against a non-numeric cached value.**
- Where: `ScormManager.cs:167` + `:688-691`.
- Problem: `WriteIfChanged(..., isReal: true)` compares with `ParseReal(known)`. If the cache holds a vocabulary value (`result = "correct"` loaded from the LMS) and the update is an estimate of `0`, `ParseReal("correct") == 0` and the write is skipped by mistake.
- Fix: only compare numerically when both strings parse as numbers (`float.TryParse`).

**L2. `ValidateScore` does not reject NaN/Infinity in `min`/`max`, or Infinity in `raw` when there are no bounds.**
- Where: `ScormManager.cs:1102-1119`.
- Problem: `ScormFormat.ToReal` turns them into `"0"`, so a silent `0` gets written.
- Fix: reject non-finite values with `ArgumentOutOfRangeException`.

**L3. Duplicate objective ids inside an interaction are not removed.**
- Where: `ScormManager.cs:586-594` / `:660-668`.
- Problem: only the ids in `objectiveIds` are deduplicated against the list. If `interaction.objectives` already has a duplicate, both are written, and a strict LMS answers 351 for `cmi.interactions.n.objectives.m.id`.
- Fix: deduplicate in `WriteInteraction`.

**L4. `UpsertObjective` only rejects ids that are empty or all whitespace.**
- Where: `ScormManager.cs:1008`.
- Problem: SCORM 2004 `long_identifier_type` (SPM 4000) is expected to be URI-like, and strict LMSs (and the ADL test suite) may answer 406 for ids with internal spaces. Today that comes back as a -1 with no explanation.
- Fix: reject internal whitespace and lengths > 4000 with a clear `ArgumentException`, or at least document it. The same applies to `objectiveIds` in `RecordInteraction`.

**L5. M4 3rd→4th changes semantics.**
- Where: `Assets/SCORM/Editor/ScormManifestBuilder.cs:119-125`.
- Problem: according to the 3rd Edition RTE (to be confirmed), with `completion_threshold` and `progress_measure` both set, the LMS evaluates `cmi.completion_status`. Mapping it to `completedByMeasure="false"` turns that off. The round trip is also asymmetric: 4th `true` → 3rd threshold keeps the evaluation.
- Status: the warning (`GetEditionWarnings`) states it honestly and the acceptance allows "mapping or warning", so it is accepted.
- Recommendation: check in SCORM Cloud that the LMS initializes `cmi.completion_threshold` with `completedByMeasure="false"`. Otherwise the mapping adds no value.

**L6. Plan deviation not recorded.**
- `plan_scorm-scenario-api.md` §2 announces `ScormEditorBackend.SimulateRelaunch()`. It does not exist; the tests use `Terminate()`+`Initialize()`.
- Fix: record it as D5 in `impl_scorm-scenario-api.md`, or implement it.

**L7. Static event and subscriber lifetime.**
- Problem: `CallCompleted` is static. A MonoBehaviour that subscribes and does not unsubscribe in `OnDestroy` leaks, and causes a caught-and-logged exception on every call after the scene changes.
- Fix: document the pattern (`OnEnable`/`OnDisable`) in the XML doc of `ScormManager.ScormCall`.

**L8. Gaps already open in the impl report (accepted).**
- M1 JS test not versioned (scratchpad).
- M5 without an automated test.
- `ScormSimulator.js` without the strict rules or resume.
- `weighting` = 0 always sent (D2, documented).

## New findings (Low, non-blocking)

**L9. `typeKnown` does not depend on the type write succeeding.**
- Where: `ScormManager.cs:714-716`.
- Problem: if the LMS rejects `cmi.interactions.n.type`, `typeKnown` is still `true` (because `type.Length > 0`), so `correct_responses`/`learner_response` are sent and get 408. These failures are now counted in `allWritten`/`LastWriteFailures`, so nothing is lost silently, but they are avoidable calls.
- Fix: `typeKnown = WriteIfChanged(...type...) && (type.Length > 0 || HasKnownValue(...))`.

**L10. Legacy setters also change `LastWriteFailures`.**
- Where: `ScormManager.cs:169-179`.
- Problem: every `SetAndCache` counts failures, but only the scenario API calls `BeginWrites()`. After a failed legacy setter (`SetLocation`, `SetSuspendData`, ...), `LastWriteFailed` may report that failure even though the XML doc describes it as "the last call of the scenario API".
- Fix: count only between `BeginWrites`/end, or document it.

**Info (not a defect).** Calls made from inside a handler do not appear in the log, because the event is suppressed. This is a deliberate trade-off against recursion and is documented.
